# TASKO ML — прогноз длительности задачи и риска срыва срока

Отдельный Python-модуль из спецификации (раздел 7). Он делает две вещи:

1. **Обучает модели** на истории задач TASKO и сравнивает алгоритмы (исследовательская часть).
2. **Отдаёт прогноз** через небольшой FastAPI-сервис, который потом будет вызывать бэкенд.

Основное приложение пока к сервису **не подключено** — это следующий шаг (этап 3 плана).

## Что внутри

```
ml/
  tasko_ml/
    schema.py     что модель знает о задаче в момент прогноза (TaskInput) и список признаков
    dataset.py    выгрузка истории из PostgreSQL, целевые переменные, синтетика для отладки
    features.py   превращение сведений о задаче в признаки (общий код для обучения и сервиса)
    models.py     кандидаты: baseline, линейная модель, Random Forest, градиентный бустинг (+LightGBM, CatBoost)
    train.py      эксперимент: разбиение по времени → сравнение → сохранение лучших → отчёт
    registry.py   реестр версий моделей (models/registry.json)
    predictor.py  прогноз по активным моделям и «главные факторы»
  service/app.py  FastAPI: /health, /models/info, /predict, /predict/duration, /predict/risk
  tests/          pytest: признаки без утечки, обучение целиком, ответы сервиса
  models/         обученные модели (в git не попадают)
  reports/        отчёты экспериментов с таблицами метрик (в git не попадают)
```

## Как это работает

**1. Целевые переменные.** Берутся только задачи в статусе «Готово»:

- *длительность* — часы от первого перехода «В работе» до «Готово»;
- *срыв срока* — 1, если задача закрыта позже дня срока (срок в TASKO — это день, поэтому закрыть
  задачу в сам день срока — вовремя).

Отменённые задачи в обучение не попадают.

**2. Признаки на момент создания задачи.** Модель видит только то, что было известно, когда задачу
завели: тип, приоритет, длину названия и описания, сколько времени до срока, день недели, подзадача
ли это, сколько у неё тегов и блокирующих задач. Плюс история исполнителя и проекта — **только по
задачам, закрытым раньше**: сколько он уже сделал, сколько часов обычно уходит, как часто срывает
сроки, сколько задач у него сейчас в работе. Имена и email в признаки не входят.

Это защита от «утечки данных» (п. 7.4): если бы модель видела будущее, на тесте она выглядела бы
отлично, а в работе ошибалась. Отдельный тест проверяет, что задачи, закрытые позже, в историю
не попадают.

**3. Разбиение по времени.** Задачи сортируются по дате создания: 70% самых ранних — обучение,
следующие 15% — выбор лучшего алгоритма, последние 15% — итоговая проверка. Так тест похож на
реальную жизнь: прогноз будущего по прошлому.

**4. Сравнение алгоритмов.** Для каждой задачи обучаются все кандидаты, включая простой baseline
(медиана длительности / средняя доля просрочек). Метрики: MAE, RMSE, R² для длительности;
Precision, Recall, F1, ROC-AUC для риска. Лучшая модель по валидации дообучается на
обучение + валидация, сохраняется в `models/` и становится активной. Таблица всех результатов
пишется в `reports/experiment-*.md` — её можно вставлять в текст работы.

**5. Прогноз.** Сервис загружает активные модели и на запрос с описанием задачи отвечает так:

```json
{
  "predictedDurationHours": 74.4,
  "deadlineRiskProbability": 0.98,
  "durationModelVersion": "duration-ridge-20261108131327",
  "riskModelVersion": "risk-logistic-regression-20261108131328",
  "topFactors": [{ "feature": "deadline_horizon_hours", "label": "Время до срока", "impact": 0.11 }]
}
```

`topFactors` — три признака, сильнее всего сдвинувшие прогноз. Вклад считается просто: насколько
изменился бы прогноз, если заменить признак на «типичное» значение из обучающей выборки.
Метод работает для любой модели; SHAP можно добавить позже.

## Запуск

Нужен Python 3.11–3.13.

```bash
cd ml
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt          # Windows
# .venv/bin/pip install -r requirements.txt            # macOS / Linux
# необязательно: LightGBM и CatBoost как дополнительные кандидаты
.venv/Scripts/pip install -r requirements-extra.txt
```

Обучение:

```bash
# на истории из базы TASKO (строка подключения как в backend/.env)
.venv/Scripts/python -m tasko_ml.train --source db --db-url "postgresql://tasko:tasko@localhost:5434/tasko"

# проверка конвейера на синтетике (научных выводов по ней не делать)
.venv/Scripts/python -m tasko_ml.train --source synthetic
```

Если завершённых задач меньше 30, модель не обучается, а отчёт объясняет почему.

Сервис:

```bash
.venv/Scripts/python -m uvicorn service.app:app --port 8001
# или в Docker, с моделями из ml/models:
docker compose --profile ml up -d ml
```

Документация API: http://localhost:8001/docs. После переобучения можно вызвать `POST /models/reload`.

Тесты:

```bash
.venv/Scripts/python -m pytest
```

## Ограничения

- Прогноз статический: делается на момент создания задачи. Повторный прогноз во время работы
  («динамический», п. 7.6) — отдельное расширение.
- Число тегов берётся текущее: в базе не хранится, когда тег добавили.
- История исполнителя считается по текущему исполнителю задачи; переназначения не учитываются.
- Текст пока используется только через длину. TF-IDF или эмбеддинги — возможное улучшение.

## Что дальше (этап 3)

- **В бэкенде:** таблицы `model_versions` и `task_predictions`, модуль `predictions`, который
  собирает `TaskInput`, вызывает сервис и сохраняет ответ.
- **Когда пересчитывать прогноз:** при создании задачи, смене исполнителя, приоритета или срока, по кнопке.
- **В интерфейсе:** риск на карточке и блок «Прогноз» в карточке задачи.
