# Проверка критериев приёмки

Критерии из раздела 16 спецификации. Для каждого указано, как его проверить, и какие автотесты его покрывают.

**Подготовка к проверке**

```bash
docker compose up -d --build            # интерфейс: http://localhost:8080, Swagger: http://localhost:8080/docs
docker compose --profile ml up -d ml    # необязательно: сервис прогноза (нужны обученные модели, см. ml/README.md)
```

Демо-пользователи (пароль у всех `Password123!`): `admin@tasko.local` — администратор,
`manager@tasko.local` — руководитель проекта, исполнители — см. `backend/prisma/seed.ts`.

**Автотесты**

| Команда | Что проверяет |
|---|---|
| `cd backend && npm test` | модульные тесты сервисов и правил (Jest) |
| `cd backend && npm run test:e2e` | интеграционные тесты API на настоящей PostgreSQL (база `tasko_test`, Supertest) |
| `cd frontend && npm test` | компоненты и вспомогательные функции интерфейса (Vitest) |
| `cd frontend && npm run test:e2e` | сквозной сценарий в браузере (Playwright, против `http://localhost:8080`) |
| `cd ml && .venv/Scripts/python -m pytest` | признаки, обучение, ответы ML-сервиса (pytest) |

## Критерии

| ID | Критерий | Статус | Как проверить вручную | Автотест |
|---|---|---|---|---|
| AC-01 | Пользователь аутентифицируется и видит только разрешённые данные | ✅ | Войти исполнителем: в «Проектах» только проекты, где он участник; чужой проект по прямой ссылке не открывается. Заблокированный администратором пользователь теряет доступ сразу | `test/app.e2e-spec.ts` — блоки AC-01, AC-02 («не показывает проект постороннему»), «Заблокированный пользователь» |
| AC-02 | Руководитель создаёт проект, участника и задачу | ✅ | Войти `manager@tasko.local` → «Новый проект» → вкладка «Участники» → добавить → «Новая задача». Назначить исполнителем не-участника нельзя | `app.e2e-spec.ts` — AC-02; `e2e/main-flow.spec.ts` |
| AC-03 | Задача проходит workflow, переходы сохраняются | ✅ | Перетащить карточку по колонкам или сменить статус в карточке задачи → блок «История» | `app.e2e-spec.ts` — AC-03; `e2e/main-flow.spec.ts` |
| AC-04 | Исполнитель работает с назначенными задачами в рамках прав | ✅ | Войти исполнителем: меняет статус своей задачи, комментирует, прикрепляет файлы; не может редактировать проект и чужие задачи | `app.e2e-spec.ts` — «исполнитель проводит свою задачу», «не может менять проект и чужие задачи» |
| AC-05 | Комментарии и вложения связаны с задачей | ✅ | Карточка задачи → «Комментарии», «Вложения» (до 10 МБ, разрешённые типы) | `app.e2e-spec.ts` — AC-05 |
| AC-06 | Доступна аналитика проекта и загрузки | ✅ | Проект → вкладка «Аналитика»: показатели, диаграмма по статусам, риски, план/прогноз/факт, загрузка исполнителей | `app.e2e-spec.ts` — AC-06; `e2e/main-flow.spec.ts` |
| AC-07 | Получается прогноз длительности корректной задачи | ✅* | При запущенном ML-сервисе карточка задачи → «Прогноз» с пометкой «Модель ML» | `ml/tests`, `predictions.service.spec.ts` |
| AC-08 | Получается вероятность срыва дедлайна | ✅* | То же: «Риск срыва срока» в процентах; значок риска на доске | `ml/tests`, `forecast.spec.ts` |
| AC-09 | Прогноз сохраняется с версиями моделей и временем | ✅ | `GET /api/tasks/:id/prediction` → история пересчётов с версиями; таблицы `task_predictions`, `model_versions` | `predictions.service.spec.ts` |
| AC-10 | После DONE сохраняются фактическая длительность и факт соблюдения срока | ✅ | Закрыть задачу → в карточке заполнены начало и завершение работы; аналитика «План, прогноз и факт» | `app.e2e-spec.ts` — «переходы сохранены в истории…», AC-06 |
| AC-11 | Сбой ML не блокирует CRUD проектов/задач | ✅ | Остановить ML-сервис (`docker compose stop ml`) → задачи создаются и меняются, прогноз помечен «По правилам» | `app.e2e-spec.ts` — AC-11 (ML-сервис намеренно недоступен) |
| AC-12 | Экспериментальный pipeline выдаёт метрики сравниваемых алгоритмов | ✅* | `cd ml && .venv/Scripts/python -m tasko_ml.train --source synthetic` → таблица метрик в `ml/reports/` | `ml/tests/test_training_and_service.py` |
| AC-13 | Проект воспроизводимо запускается Docker Compose | ✅ | `docker compose up -d --build` → http://localhost:8080 | — |
| AC-14 | API документирован OpenAPI/Swagger | ✅ | http://localhost:8080/docs (или http://localhost:3100/docs) | — |

\* Механизм работает, но модели пока обучены на синтетических данных: для научных выводов нужно обучение на реальной истории задач (см. `ml/README.md`).

## Известные ограничения

- Переходы между статусами свободные (из любого в любой) — решение проекта, расходится со строгой схемой раздела 6.4.
- Email/push-уведомления не входят в MVP (раздел 6.6): уведомления о задачах приходят только внутри системы.
- Сквозной идентификатор запроса в логах (раздел 14) не реализован.
